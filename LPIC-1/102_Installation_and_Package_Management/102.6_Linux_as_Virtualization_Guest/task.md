**Практическая работа №1: Определение виртуализации**

**Задание:**
1. Определите, запущена ли система в виртуальной машине.
2. Узнайте тип гипервизора.
3. Посмотрите сведения о системе (производитель, модель).
4. Проверьте, установлены ли гостевые драйверы (qemu-guest-agent).
5. Объясните, зачем нужны гостевые драйверы.

**Решение и пояснения:**
```bash
systemd-detect-virt                 # 1-2. Тип виртуализации (kvm, vmware...)
dmidecode -s system-manufacturer    # 3. Производитель системы
dmidecode -s system-product-name    # 3. Модель
systemctl status qemu-guest-agent   # 4. Гостевой агент
```
**Пояснения:**
`systemd-detect-virt` определяет среду (none для физической машины). `dmidecode` читает DMI/SMBIOS. Гостевые драйверы и агенты (например, `qemu-guest-agent`) обеспечивают корректное завершение, синхронизацию времени и обмен данными с гипервизором.

**Практическая работа №2: Подготовка системы после клонирования**

**Задание:**
1. Сгенерируйте новый machine-id.
2. Измените имя хоста на `clone01`.
3. Удалите старые SSH-ключи хоста.
4. Сгенерируйте новые SSH-ключи хоста.
5. Объясните, почему это критично после клонирования.

**Решение и пояснения:**
```bash
sudo rm /etc/machine-id && sudo systemd-machine-id-setup   # 1. Новый machine-id
sudo hostnamectl set-hostname clone01                       # 2. Имя хоста
sudo rm -f /etc/ssh/ssh_host_*                              # 3. Удаление старых ключей
sudo ssh-keygen -A                                          # 4. Генерация новых ключей
sudo systemctl restart ssh                                  # 4. Перезапуск SSH
```
**Пояснения:**
Клонирование дублирует machine-id и SSH-ключи хоста. Дубли machine-id ломают DHCP/D-Bus/логирование, а одинаковые ключи хоста угрожают безопасности (MITM). После клонирования обязательно перегенерируют machine-id и ключи хоста.

**Практическая работа №3: Работа с cloud-init**

**Задание:**
1. Проверьте, установлен ли cloud-init.
2. Создайте простейший файл `user-data` для создания пользователя.
3. Создайте файл `meta-data` с именем инстанса.
4. Покажите, как эти файлы передаются через ISO/NoCloud.
5. Объясните назначение cloud-init.

**Решение и пояснения:**
```bash
cloud-init --version                          # 1. Проверка установки
cat > user-data <<'EOF'
#cloud-config
users:
  - name: student
    sudo: ALL=(ALL) NOPASSWD:ALL
    shell: /bin/bash
EOF
echo "instance-id: iid-001" > meta-data       # 3
genisoimage -output seed.iso -volid cidata -joliet -rock user-data meta-data   # 4
```
**Пояснения:**
cloud-init инициализирует облачные инстансы при первом запуске: настраивает сеть, пользователей, SSH-ключи. Данные берутся из источника (NoCloud, EC2, OpenStack). Формат `user-data` — YAML с директивой `#cloud-config`.

**Практическая работа №4: Клонирование и шаблоны**

**Задание:**
1. Очистите кэш apt перед созданием шаблона.
2. Очистите журналы и временные файлы.
3. Обнулите свободное место (опционально).
4. Перечислите, какие уникальные данные нужно удалить из шаблона.
5. Объясните разницу между виртуальной машиной и контейнером.

**Решение и пояснения:**
```bash
sudo apt clean                       # 1. Очистка кэша пакетов
sudo journalctl --rotate; sudo journalctl --vacuum-time=1s  # 2. Очистка журналов
sudo rm -rf /tmp/* /var/tmp/*        # 2. Временные файлы
# 4. Уникальное: /etc/machine-id, /etc/ssh/ssh_host_*, ~/.bash_history, cloud-init состояние
sudo cloud-init clean --logs         # Сброс состояния cloud-init
```
**Пояснения:**
Перед превращением ВМ в шаблон удаляют уникальные данные (machine-id, ключи хоста, история, сетевые настройки), чтобы клоны не конфликтовали. ВМ виртуализирует оборудование и имеет своё ядро; контейнер делит ядро хоста и изолирует процессы через namespaces/cgroups.
